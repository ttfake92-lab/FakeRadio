# ADR 目录说明

## 目的

`docs/adr/` 用来记录 FakeRadio 的重要架构决策，避免后续实现只能靠提交历史或对话回忆来猜原因。

只有真正会影响边界、contract、运行策略或长期维护方式的决策，才需要写 ADR。

## 什么时候写 ADR

出现以下情况时，优先补一篇 ADR：

- 调整系统边界，例如把逻辑从前端移到 server，或反过来。
- 引入新的核心依赖，例如更换 WebSocket、数据库、任务调度方案。
- 改变 shared contract 的组织方式。
- 接入真实 provider，并且这个接入方式会影响后续所有 adapter。
- 修改状态模型、记忆模型、调度策略等长期规则。

## 文件命名

建议使用递增编号加短标题：

```text
0001-local-first-architecture.md
0002-shared-contract-boundary.md
0003-music-adapter-strategy.md
```

标题中的 slug 可以保留英文，正文默认使用中文。

## 推荐结构

每篇 ADR 建议包含以下部分：

```md
# ADR 0001: 决策标题

## 背景

## 决策

## 影响

## 备选方案

## 后续动作
```

## 写作原则

- 只记录“为什么这样定”，不要把实现细节全部塞进 ADR。
- 语言尽量直接，避免模糊词。
- 必须自包含，不依赖截图、聊天记录或临时上下文。
- 如果决策被推翻，不删除旧 ADR，而是新增一篇说明替代关系。

## 与其他文档的关系

- `CONTEXT.md` 负责描述当前稳定的共同语言和总体边界。
- `docs/architecture.md` 负责给出整体架构视图。
- `docs/adr/*.md` 负责解释“某个重要决策为什么是这样”。

三者各司其职，避免互相重复。
