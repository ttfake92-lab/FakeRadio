# A-09 播放时服务端录制音频流（架构决策）

Status: needs-triage
Type: HITL

## Parent

## What to build

为支持导出完整音频（A-10、A-12），服务端需要在播放某首歌时，将其完整音频数据保存到本地磁盘。

当前架构：服务端通过 music adapter 获取音频 URL，前端直接从该 URL 拉取音频流播放，服务端不经手音频字节。

**需要决定的架构方向：**

**方案 A（推荐）：服务端透明代理录制**
- 新增 `GET /api/audio/:trackId` 代理路由
- 前端改为通过这个代理 URL 播放，服务端在转发字节的同时写入本地文件
- 优点：对前端透明，录制与播放同步，不重复下载
- 缺点：服务端带宽翻倍（同时转发给前端 + 写盘）

**方案 B：服务端独立下载**
- 用户收藏某首歌或触发导出时，服务端重新独立下载一次完整音频
- 优点：不影响实时播放路径
- 缺点：歌曲可能是流式 URL（有效期），重复下载可能失效

**方案 C：前端录制上传**
- 前端录制 Web Audio 输出，完成后 POST 到服务端保存
- 缺点：体积大、耗前端资源、实现复杂

## 需要用户确认的决策

1. 选择哪个方案？（推荐 A）
2. 能接受为每首「有互动」的歌在本地存储完整音频文件（一首歌约 5-20MB）吗？
3. 依赖 FFmpeg 做后续混音（A-10）是否可以接受？
